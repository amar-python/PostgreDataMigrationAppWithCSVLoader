OIT-001  Concurrent start-up migrations fail
------------------------------------------------------------------
Severity            : High
Status              : CONFIRMED (R1, at the `alembic upgrade head` level; two full API
                      processes were not started)
Area                : Concurrency / migration atomicity / operational readiness
Evidence location   : alembic/env.py:33-40 (CREATE SCHEMA IF NOT EXISTS, commit, then
                      migrations in one transaction; no advisory lock);
                      api/db.py:192-246 (bootstrap runs `alembic upgrade head` on every
                      start; only OperationalError is handled, so IntegrityError aborts
                      start-up); api/main.py:73 (bootstrap in lifespan);
                      api/tenancy.py:22,155 (control migrations use a process-local
                      threading.Lock only). Log: review_work/logs/repro_concurrent_migrate.
Affected requirement: PROPOSED BR-50; HANDOFF F5; BR-37/BR-38 deployment
Impact              : Two replicas or workers starting against a new database: one
                      fails to start. With an orchestrator restart it usually recovers,
                      but first deployments and scale-out are unreliable; the same race
                      on a pending migration at upgrade time is untested.
Remediation         : Take pg_advisory_lock (session level) in alembic/env.py around
                      schema creation and migration, or run migrations as a single
                      pre-start job and stop running them in every API process.
Acceptance criteria : 10 of 10 trials of two concurrent bootstrap() calls (fresh DB and
                      DB one revision behind) both succeed; alembic_version = head; no
                      UniqueViolation. The test fails with the lock removed.
Verification method : Test (concurrency, negative control) + Inspection
Dependencies        : None. Note: tenant T&E migrations already use an advisory lock
                      (api/tenancy.py:132-167) - reuse the pattern.

OIT-002  T&E upload drops a dynamic dataset table without the destructive flag
------------------------------------------------------------------
Severity            : High
Status              : CONFIRMED (R2)
Area                : Data integrity / security (authorisation)
Evidence location   : api/services/te_loader.py:88-118 (_cleanup_prior_registry_entries
                      drops csv_* tables whose file_hash matches), called at 321;
                      te_loader.py:226-234 (only _require_delete is checked);
                      api/services/destructive_ops.py:48-51 (_require_delete returns at
                      once when session is None); api/routers/csv_routes.py:308
                      (API_ALLOW_DESTRUCTIVE is checked only on the DELETE route).
Affected requirement: BR-31 (open item, #175), BR-24, BR-30 (decision 2), PROPOSED BR-51;
                      SECURITY_REVIEW_PACK F8
Impact              : A shared-key caller (or a signed-in role with delete permission)
                      can destroy a versioned dataset's table by uploading the same bytes
                      in T&E mode, with API_ALLOW_DESTRUCTIVE off and no warning. The
                      registry row is deleted too. The original bytes survive in
                      upload_blobs, but the imported table and its edits/lineage do not.
Remediation         : Never drop a dynamic dataset from the T&E path (match T&E entries
                      only), or refuse with 409. If replacement is kept, require both
                      delete permission and API_ALLOW_DESTRUCTIVE, including for the
                      shared key.
Acceptance criteria : With the flag off, R2 leaves the dynamic table and its registry row
                      in place (or returns 403/409), with and without a session. The
                      regression test fails on the current code.
Verification method : Test
Dependencies        : OIT-013 (shared-key scope)
